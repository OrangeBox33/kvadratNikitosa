# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Приложение для совместного рисования пикселями в реальном времени, которое управляет **физической LED-матрицей 16×16 на WS2812B** (256 светодиодов), подключённой к ESP32. Пользователь рисует на сайте; каждый штрих по WebSocket рассылается всем остальным браузерам *и* физической панели(ям), которые в реальном времени зажигают соответствующие пиксели. Панелей может быть несколько (каждая — именованный ESP32), все они отображают одну общую сетку.

Части проекта:

- **Клиент** (`src/`) — React 18 + Redux Toolkit + styled-components, сборка через **Vite**. Корень этого репозитория.
- **Сервер** (`server/`) — Node.js + Express + `ws`, TypeScript с ESM (NodeNext). Свой собственный `package.json`.
- **Общий код** (`shared/`) — константы, типы и enum сообщений, которые обязаны совпадать у клиента и сервера. Импортируется обеими сторонами. Свой минимальный `package.json` с `"type": "module"`, чтобы сервер (NodeNext) видел его как ESM.
- **Прошивка** (`kvadrat.ino`) — скетч Arduino/ESP32. **Не в этом репозитории** — лежит по пути `/Users/simpson/Documents/Arduino/kvadrat/kvadrat.ino`.

## Команды

Клиент (из корня репозитория):

```bash
npm start            # (= npm run dev) Vite dev server на :3000, HMR, открывает браузер
npm run build        # production-сборка -> dist/ (три страницы: index/wifi/update)
npm run preview      # локальный предпросмотр собранного dist/
npm run lint         # eslint --fix по src/**/*.{ts,tsx}
```

Сервер (из папки `server/`):

```bash
npm install
npm run build        # tsc: *.ts + ../shared/*.ts -> server/dist/ (см. server/tsconfig.json)
npm start            # node dist/server/server.js
```

⚠️ Точка входа сервера теперь `dist/server/server.js` (а не `dist/server.js`), потому что в компиляцию включён `../shared`, и tsc сохраняет структуру папок (`dist/server/…` + `dist/shared/…`). Деплой/процесс-менеджер должен запускать именно этот путь (или `npm start`). Перед пересборкой стоит удалить старый `server/dist`, чтобы не остались устаревшие файлы с прежней раскладки.

Тестов в проекте нет — тестовый раннер нигде не настроен.

Не запускай проверки компиляции/типов (`tsc`, `npx tsc --noEmit`, сборку и т.п.) для верификации своих правок — владелец проверяет изменения сам.

## Архитектура

### Модель данных (общая концепция для всех трёх частей)

- Холст — это плоский массив из 256 цветовых строк (`Grid = string[]`), индексация `id = row * 16 + col` (`id` 0–255, по строкам, начало отсчёта в левом верхнем углу). Эта же индексация используется в клиенте, сервере и в математике рисования.
- **Pixel** — это `{ id, color }`; по сети при рисовании передаётся пачка таких пикселей.
- Цвета везде в JS/TS — hex-строки (`#RRGGBB`). Цвет по умолчанию/«пустой» отличается по слоям: клиент рисует пустой пиксель как `#303030` (`DEFAULT_COLOR` в `src/utils/constants.ts`), сервер хранит пустой как `#000000` (`server/constants.ts`).

### Поток сообщений на клиенте

`src/socket/socket.ts` открывает единственный `ReconnectingWebSocket` на `wss://kvadratnikitosa.ru` — это единственный входящий канал; он диспатчит Redux-экшены в зависимости от `type`, сравнивая с `EMessageTypes` из `shared/enums.ts` (`getGrid`, `getChat`, `draw`, `sendToChat`, `wifi`, `ota`).

Исходящие сообщения идут через **thunk'и** в `src/redux/thunk.ts`, никогда напрямую из компонентов:
- `setAndSendPixel(id)` — основной экшен рисования (единая ветка для кисти и карандаша). `candidateIds` = окрестность 3×3 (`needPaintPixels` в `src/utils/utils.ts`, вручную обрабатывает края/углы) для `BRUSH` или `[id]` для `PENCIL`, затем фильтр «только реально меняющие цвет» → оптимистичное обновление сетки → запись в историю undo → отправка `{ type: EMessageTypes.DRAW, pixels }`.
- `undo()` — откатывает **весь последний мазок целиком** (см. группировку истории ниже) и повторно отправляет пиксели как `draw`.
- `sendMessage(...)` — чат.

Состояние живёт в одном Redux-слайсе (`src/redux/slice.ts`, стор — это напрямую редьюсер слайса, то есть `RootState` *и есть* `MainState`, без вложенности). Клиентская история undo (`UNDO_SIZE = 100`) отдельна от серверной истории для воспроизведения.

**Группировка истории отмены по мазку.** Начало мазка (`onTouchStart` в `Grid`, `onMouseDown` в `Pixel`) диспатчит `beginStroke()`, взводящий флаг `pendingNewStroke`. Первый реальный пиксель мазка создаёт новую группу истории и сбрасывает флаг; остальные пиксели мазка дописываются в ту же группу (`pushHistory`). Поэтому один `undo()` откатывает мазок целиком. Дедуп внутри мазка обеспечен фильтром «цвет реально меняется» — повторный проход по уже закрашенному пикселю ничего не добавляет.

Компоненты (`src/components/`) разделены по типу устройства: `Main/index.tsx` в рантайме выбирает `Desktop` / `Mobile` / `MobileRotate` через хук `useDeviceType` (`src/utils/hooks.ts`, возвращает `0`=десктоп, `1`=портрет, `2`=короткий ландшафт). У большинства компонентов есть варианты `Desktop/` и `Mobile/` плюс рядом лежащий `*.styled.tsx`. Ввод рисования ловится в `Grid/index.tsx` через координаты касания → id пикселя.

Есть **три отдельные HTML-точки входа** — в Vite это сами HTML-файлы в корне репозитория, каждый подключает свой скрипт: `index.html` → `src/index.tsx` (приложение для рисования), `wifi.html` → `src/wifi.tsx` (передаёт панели Wi-Fi-учётные данные), `update.html` → `src/update.tsx` (UI OTA-обновления прошивки: кнопка шлёт `{ type: 'ota', pathname }`, панель определяется по URL `/update/<имя>`, как у wifi). Список входов продублирован в `build.rollupOptions.input` в `vite.config.ts`. Плагин `clean-url-rewrites` там же в dev отдаёт нужный HTML на «чистых» путях `/wifi` и `/update` (в проде этим занимается nginx/сервер).

### Сервер (`server/server.ts`) — центральный узел

Запускает **два WebSocket-сервера на разных портах** — это разделение центрально для работы всей системы:

- **Браузерные клиенты**: `WebSocketServer({ server })`, разделяющий HTTP-сервер Express на **порту 3500** (nginx терминирует TLS и проксирует сюда `wss://kvadratnikitosa.ru`). Текстовые JSON-сообщения. Хранятся в множестве `clients`.
- **Панели ESP32**: *отдельный* `WebSocketServer({ port: 81 })`. **Бинарные** сообщения. Хранятся в множестве `arduinoClients`. ESP32 подключаются напрямую к `93.183.69.206:81` (см. `serverIp`/`serverPort` в прошивке), минуя nginx.

Типы сообщений — общий enum `EMessageTypes` из `shared/enums.ts` (`server/enums.ts` его ре-экспортит): `getGrid`, `getChat`, `draw`, `sendToChat`, `wifi`, `ota`.

При `draw`: сервер обновляет авторитетную `grid`, записывает кадр в кольцевой буфер `history` (`HISTORY_SIZE = 400`, используется для воспроизведения — это *не* то же самое, что клиентский undo), рассылает пиксели всем *остальным* браузерным клиентам как JSON и пушит их на каждую панель как бинарь.

**Чат заодно работает как командный канал.** Два «магических» сообщения (где username === text) запускают анимации на панелях вместо отправки в чат: `PLAY_HISTORY = '42'` проигрывает всю записанную историю на панелях кадр за кадром; `RESET_HISTORY = '228'` очищает историю воспроизведения. См. `server/constants.ts`.

Состояние сохраняется в `server/save.json` каждые 60с (функция `saveState`) и загружается при старте (grid, oldGrid, history, chat и т.д.). Если файла нет — сервер создаёт его с начальным состоянием, так что первый запуск на чистой машине не падает.

### Бинарный протокол Сервер → ESP32 (`server/helpers.ts` + прошивка)

Это самый хитрый и неявный контракт в кодовой базе. Сообщения на панели — это `Uint8Array`. **Байт 0 — тег действия** (`EArduinoActions`): `GRID=1`, `DRAW=2`, `HISTORY=3`, `HISTORY_SPLIT=255`. После тега пиксели упакованы повторяющимися **группами по 4 байта: `[r, g, b, id]`**. Прошивка читает группы по 4 начиная со смещения 1 и вызывает `FastLED` (`payload[0]` 1 или 2 → рисуем сразу; 3 → анимация, где значение байта `255` служит разделителем кадров, вызывающим `FastLED.show()` + задержку).

Перед отправкой на сервере происходят два преобразования:
- **Яркость**: каждый канал RGB делится на `BRIGHTNESS_DEVISION = 4` (0–255 → 0–63), чтобы панель не слепила.
- **Змейка / serpentine-ремап** (`convertIdForArduino`): физическая LED-лента разведена бустрофедоном (каждый второй ряд идёт справа налево), поэтому у чётных рядов индекс столбца зеркалится. Любое изменение индексации светодиодов должно оставаться согласованным с физической разводкой.

### Прошивка (`kvadrat.ino`, внешний путь выше)

ESP32 + FastLED (WS2812B на `DATA_PIN 13`, `NUM_LEDS 256`). При загрузке читает Wi-Fi-учётные данные из `Preferences` (при их отсутствии откатывается на захардкоженные `default_ssid`/`password`), подключается к WebSocket-серверу и отправляет свой **chip id** (из `ESP.getEfuseMac()`) первым текстовым сообщением. Сервер сопоставляет chip id ↔ имя панели через `CHIP_TO_NAME`/`NAME_TO_CHIP` в `server/constants.ts` (`sp`, `luchik`, `sega`, `my`). Сообщение типа `wifi`, направленное на именованную панель, отправляет новые учётные данные `"ssid:password"`, которые ESP32 сохраняет и перезагружается. Heartbeat — ping/pong каждые 30с с обеих сторон.

### OTA-обновление прошивки (httpUpdate)

Модель **pull**: сервер лишь даёт команду, скачивает `.bin` сама панель — это работает, даже когда панель не в одной сети с разработчиком.

- **Триггер идёт по существующему текстовому каналу**, по той же механике, что и wifi (адресная отправка конкретной панели по имени). UI на `/update/<имя>` (`src/components/Update`) шлёт `{ type: 'ota', pathname }`; сервер (`server.ts`) находит панель по `pathname.split('/')[2]` и отправляет ей текстовую команду `"OTA"`. Маршруты `/update/<имя>` регистрируются в `server.ts` циклом по `NAME_TO_CHIP` (зеркало wifi).
- **В прошивке** ветка `WStype_TEXT` проверяет `message == "OTA"` **до** разбора `ssid:password` (иначе спутается), отключает WebSocket, чтобы heartbeat не рвал загрузку, и через `httpUpdate.update(client, firmwareUrl)` качает образ. `rebootOnUpdate(true)` перезагружает панель на новый образ; при ошибке — переподключение к WS и работа на старой прошивке.
- **`firmwareUrl` обязан быть плоским `http://` без редиректа на `https`.** Иначе `httpUpdate` пойдёт за редиректом на TLS, потянет mbedTLS и раздует бинарь. По этой же причине используется `WiFiClient`, а НЕ `WiFiClientSecure`. TLS не нужен: панель и так ходит на сервер по plain `ws://` (порт 81, прямой IP), TLS терминирует nginx только для браузеров.
- **OTA требует двух app-разделов.** У флеша 4 MB дефолтная схема даёт `app0`/`app1` по 1.25 MB (образ ~1.05 MB — влезает впритык). Рекомендуемая схема — **«Minimal SPIFFS (1.9MB APP with OTA / 190KB SPIFFS)»**: слоты ~1.9 MB, `spiffs` не используется (креды лежат в `nvs`/`Preferences`). Раздачу `.bin` настраивает nginx (`location /fw/`); чек-лист ручных шагов — в `todo.md`.

## Соглашения и подводные камни

- **Форматирование**: табы, ширина 4, `printWidth` 100, одинарные кавычки (JS) / двойные (JSX). См. `.prettierrc.json`.
- **`shared/` — единственный источник для общего.** Туда кладём только то, что *обязано* совпадать у клиента и сервера: размер сетки (`DEFAULT_X/Y/SIZE`), enum `EMessageTypes`, структуры данных (`Pixel`, `Grid`, `ChatMessage`, …). Клиент импортит напрямую (Vite резолвит `.ts`), сервер — с расширением `.js` (`from '../shared/enums.js'`). `src/utils/constants.ts` и `server/constants.ts` ре-экспортят общие константы и добавляют свои, специфичные. `server/types.ts` заворачивает общие типы в прежние `T…`-алиасы, чтобы не трогать остальной серверный код.
- **НЕ клади в `shared/` то, что по слоям отличается**: цвет пустого пикселя (клиент `#303030` / сервер `#000000`), размеры чата/истории/undo, палитра, `EArduinoActions`, `NAME_TO_CHIP` — это остаётся раздельным.
- **Импорты на сервере используют расширение `.js`** в TS-исходниках (в т.ч. на `../shared/*.js`) — этого требует `module: NodeNext`. У `server/tsconfig.json` `rootDir: ".."` и в `include` добавлен `../shared`, поэтому сборка ложится в `dist/server/…` + `dist/shared/…`.
- Chip id в `NAME_TO_CHIP` — специфичные для железа значения, производные от MAC; не выдумывай их. Добавление панели означает добавление её реального chip id в обе мапы в `server/constants.ts`.
- `ssl/` (сертификаты) и `save.json` в gitignore / зависят от окружения и в свежем клоне отсутствуют.
